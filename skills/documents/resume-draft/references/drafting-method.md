# 組み立ての進め方

## 何を作るか

職務経歴書は、応募先が「この人はこの仕事の何を、どの範囲で、どれくらいやってきたか」を読み取るための書類である。成果物は**利用者の素材だけで書かれた下書き1通**と、要件との対応表である。素材にないことは書かない。足りない箇所は質問として返す。

素材は `career-inventory` の結果を使う。棚卸しの段階で決まっていない役割や裏づけは、ここでも決まっていないものとして扱う。書きやすくするために役割を上げたり、数値を丸めて断定したりしない。

## 形式の選び方

| format | 並べ方 | 向いている場面 | 注意 |
| --- | --- | --- | --- |
| `reverse_chronological` | 新しい在籍期間から古い方へ | 中途の多くの場面。直近の仕事が応募職種に近いとき | 古い期間を省かない。短くしてよい |
| `chronological` | 古い在籍期間から新しい方へ | 経歴が長くない、または一貫した積み上げを見せたいとき | 直近の仕事が最後に来るため、職務要約で先に示す |
| `functional` | 職務・スキルの種類ごと（キャリア式） | 転職回数が多い、同じ種類の仕事を複数の会社で続けてきた、応募職種と直近の仕事が離れているとき | 在籍期間の一覧は別に必ず載せる。いつの経験かが読めなくならないようにする |

応募先や媒体が様式や形式を指定している場合はそれに従う。どれを選んだかと、その理由を1行で残す。形式の選択は好みの問題でもあるため、利用者が別の形式を選んだらそれに従う。

## 構成

| 節 | 何を書くか | 素材 |
| --- | --- | --- |
| 職務要約 | 経歴の全体像を数行で。何の仕事を、どの範囲で、何年 | 本文に載せた事実だけ |
| 職務経歴 | 在籍期間ごと（キャリア式は職務ごと）に、会社、期間、所属、担当業務、主な経験 | 棚卸しの経験 |
| 活かせる経験・知識・技術 | 応募先の要件に対応するもの | 本文で示した経験と、確かめられるツール・言語 |
| 資格 | 名称と取得年月 | 利用者の申告。取得見込みは見込みと書く |
| 自己PR | 本文の事実から、応募先で役立つと利用者が考える点を2〜3つ | 本文に載せた事実だけ |

**職務要約と自己PRに、本文にない強みを書かない。** 要約を先に書くと、要約に合わせて本文を盛る順序になりやすい。本文を先に固める。

会社の事業内容、従業員数、売上などを書く場合は、公開情報で確かめられるものに限り、時点を利用者に確かめる。

## 要件との対応

求人票の必須要件・歓迎要件を1行ずつ、原文で置く。各要件に、それを示せる経験を対応させる。

- 「経験3年以上」のような年数の要件は、経験の中身ではなく在籍期間の長さで確かめる。スクリプトの `outline` に期間ごとの月数が出る。
- **対応する経験がない必須要件を埋めない。** 選択肢は3つ。近い経験があるかを利用者に聞く、載せずに面接で説明する、応募の判断に戻す（`job-posting-analysis`）。どれにするかは利用者が決める。
- 要件の語句を本文に入れるのは、同じ事実を相手に通じる言葉にするときだけ。担当範囲・規模・期間を広げて語句に合わせない。
- どの要件にも対応しない経験を載せるかは、利用者が決める。職歴の全体像として必要なら短く残す。

## 裏づけに合わせた書き方

| evidence | 書き方 |
| --- | --- |
| `public` / `record` | 数値を断定形で書いてよい。守秘の範囲を先に確かめる |
| `third_party` | 事実は書ける。数値は資料で確かめられるまで断定しない |
| `memory` | 行動と変化は書ける。数値は使わないか、幅のある規模の言葉（「数十社」「複数部署」）にする。記憶の数字に「約」を付けて残さない |
| `unknown` | 書く前に確かめる。確かめられなければ載せない案も出す |

「約」「およそ」を付けても、推測した数値であることは変わらない。記憶だけの数値に「約」を付けて載せる案を出さない。

人から聞いただけの結果（「解約率が下がったと聞いた」）は、その場にいた人の確認ではないため `third_party` ではなく `memory` として扱う。数値のない結果は `metrics` に入れず、本文で「〜と聞いている」と書くか、確かめられるまで載せない。

自分の成果でも、社内資料（評価面談の資料、社内の実績表）から取った数値は、社外に出してよいかを利用者に確かめる。出せない場合は守秘情報として抽象化する。

## 役割の書き分け

| role | 書き方 |
| --- | --- |
| `owner` | 自分が決めたこと、責任を持った範囲を主語「私」で書く |
| `member` | 担当範囲を明示し、その範囲の行動と結果を書く |
| `team` | 成果の主語はチームにする。その中で自分が担った部分を分けて書く |
| `unstated` | 書く前に担当範囲を確かめる。確かめられるまで、チームの成果として書く |

チームの成果を自分の成果として書くと、面接で具体を聞かれたときに崩れる。

## 守秘情報の抽象化

未公開の数値、顧客名、契約条件、社内資料の内容、未公開の技術情報は、規模感を保って特定できない形にする（「大手小売の顧客」「年間数億円規模の案件」）。抽象化しても業界や時期から特定できる場合は載せない。どう抽象化したかを利用者に示し、利用者が確かめる。

## 空白期間と重なり

在籍期間の間の空白、短期の在籍は、事実のとおりに書く。期間をずらす、在籍を省く案を出さない。書き方の選択肢（学習・療養・家族の事情などを書くか、期間だけ書くか）は並べるが、何を書くかは利用者が決める。下書きではどちらかを既定にせず、両案を並べる。面接での説明は `interview-prep` に渡す。

期間が重なる場合は、兼務・副業・入力の誤りのどれかを確かめる。副業を書くかどうかも利用者が決める。

## スクリプト入力

`scripts/check_resume_plan.py` は、要件との対応、裏づけ、役割、期間を数え、並び順の骨組みを作るだけで、文章の良し悪しも通過の見込みも判定しない。`career-inventory` の入力に、`include`、`supports`、`abstracted` と応募先の要件を足した形になっている。

```json
{
  "track": "chuto",
  "format": "reverse_chronological",
  "as_of": "2026-09",
  "target": {
    "label": "架空商事 法人営業",
    "requirements": [
      {"id": "r1", "text": "法人営業の経験3年以上", "level": "must"},
      {"id": "r2", "text": "SaaSの導入支援の経験", "level": "want"}
    ]
  },
  "timeline": [
    {"label": "架空A社", "start": "2018-04", "end": "2022-03"},
    {"label": "架空B社", "start": "2022-06", "end": null}
  ],
  "experiences": [
    {
      "id": "e1",
      "title": "中堅製造業向けの新規開拓",
      "timeline_label": "架空A社",
      "kind": "sales",
      "role": "member",
      "evidence": "record",
      "metrics": [{"text": "新規受注18社", "evidence": "record"}],
      "confidential_risk": false,
      "include": true,
      "supports": ["r1"]
    },
    {
      "id": "e2",
      "title": "既存顧客への管理ツールの導入支援",
      "timeline_label": "架空B社",
      "kind": "improvement",
      "role": "owner",
      "evidence": "memory",
      "metrics": [{"text": "解約率を半減", "evidence": "memory"}],
      "confidential_risk": true,
      "abstracted": true,
      "include": true,
      "supports": ["r1", "r2"]
    }
  ]
}
```

- `track` は `chuto` / `shinsotsu`。`format` は上の表の値か `unknown`。
- `as_of` は、在籍中（`end` が `null`）の期間がある場合に必要。
- `target` は省略できる。省略すると汎用版として扱う。`requirements[].level` は `must` / `want`。
- `experiences[].include` は載せるなら `true`、載せないなら `false`。決めていなければ省略する。
- `supports` は、その経験が示す要件の `id`。対応を付けるのは利用者で、スクリプトは付いた対応を数えるだけである。
- `role`、`evidence`、`metrics[].evidence`、`kind` の値は `career-inventory` と同じ。`metrics` には数値を含む主張だけを入れる。
- `abstracted` は、守秘情報の抽象化を決めたか。`confidential_risk` が `true` のときに使う。

実行:

```bash
python3 scripts/check_resume_plan.py input.json
```

出力の `requirements` は要件ごとの対応する経験、`outline` は選んだ形式での並び順（キャリア式では種類ごとのまとまりと在籍期間の一覧）、`gaps` と `overlaps` は在籍期間の空白と重なり、`flags` は下書きの前に決めること。

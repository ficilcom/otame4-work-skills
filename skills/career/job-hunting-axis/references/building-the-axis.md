# 軸の作り方

## 軸とは何か

軸は「やりたいこと」の宣言ではなく、**応募先を選ぶときに実際に使う基準**である。使えるかどうかは、次の1点で決まる。

> **何を見れば、その基準を満たしているか確認できるか。**

確認方法が言えない基準は、候補を選ぶのに使えない。「成長できる環境」「風通しが良い」「若いうちから裁量がある」は、そのままでは基準にならない。**基準として悪いのではなく、まだ確認方法が決まっていないだけである。** 捨てずに、確認方法を作る。

| そのままの言葉 | 何を見れば確認できるか（例） |
| --- | --- |
| 成長できる環境 | 入社1〜3年目が任される範囲、研修の期間と内容、異動の実績 |
| 風通しが良い | 意思決定に誰が関わるか、面談の頻度、反対意見が出た直近の例 |
| 若いうちから裁量がある | 何を自分で決められるか、決裁の範囲、若手の担当案件の規模 |
| 安定している | 事業の柱の数、直近数年の業績、公開されている財務情報 |

確認方法は、**公開情報で見るもの**（`company-research`）、**求人票・労働条件で見るもの**（`job-posting-analysis`、`offer-terms-check`）、**面接で聞くもの**（`interview-prep`）に分かれる。どこで確認するかまで決めて、初めて軸になる。

## 3種類に分ける

| kind | 意味 | 使い方 |
| --- | --- | --- |
| `must` | 満たされなければ受けない | 候補を絞る |
| `want` | あると良いが、なくても受けうる | 候補を比べる |
| `avoid` | あったら受けない | 候補を外す |

**`avoid` を必ず1つ以上挙げる。** 欲しいものだけを並べると、外すべき候補を判別できない。「これがあったら無理」は、たいてい「これが欲しい」より正確に言える。

`must` が多すぎると候補が残らない。ただし**多いこと自体は誤りではない。** 問題になるのは、候補が残らなかったときに**何を緩めるかが決まっていない**ことである。全部が `must` の状態は、緩める順序がないという意味になる。

## 何に基づく軸か

同じ言葉でも、どこから来た基準かで確認の重みが変わる。

| basis | 何に基づくか | 扱い |
| --- | --- | --- |
| `experience` | 自分が実際に経験した | 強い。ただし1社の経験を一般化していないか見る |
| `observed` | 人から聞いた、見て知っている | 中。誰の、いつの話かを確認する |
| `assumption` | 想像。やったことはない | **否定しない。ただし先に確かめる** |
| `unknown` | なぜそう思うのか未確認 | 言語化するところから始める |

**新卒では `assumption` が多くなるのが自然である。** 働いたことがないのだから当然で、それを「甘い」と評価しない。やることは1つ、**確かめる方法を決める**ことである。インターン、OB・OG訪問、公開情報、面接での質問。

中途では、`experience` に基づく軸が、**現職1社の経験の一般化**になっていないかを見る。「この会社がこうだったから、どこでもこうだ」とは限らない。

## 両立しにくい組み合わせ

軸どうしがぶつかることがある。ぶつかること自体は問題ではない。**両方を `must` にしたまま探し続けることが問題になる。**

- 裁量が早い ↔ 研修が手厚い
- 給与が高い ↔ 労働時間が短い
- 転勤がない ↔ 事業領域が広い
- 安定している ↔ 新しいことができる

ぶつかる組み合わせを見つけたら、**どちらを緩めるかを先に決める。** 候補が0件になってから決めると、焦って決めることになる。

## 候補に当てて確かめる

軸は、候補に当ててみるまで使えるか分からない。3〜5社に当ててみて、次を見る。

- **全社が同じ判定になる軸** — 差がつかないので、選ぶのに使えていない
- **判定できない軸** — 確認方法が足りない
- **未確認が多い候補** — 調べていないだけ。**未確認を不適合として外さない**

軸は動く。候補を見て変わるのは失敗ではなく、確かめた結果である。**最初に決めた軸を守り続けない。** 変えた場合は、なぜ変えたかを記録する。

## スクリプト入力

`scripts/check_axis.py` は基準が使える形になっているかを確認するだけで、基準の当否も候補の優劣も判定しない。

```json
{
  "track": "shinsotsu",
  "criteria": [
    {
      "id": "a1",
      "text": "入社3年目までに顧客と直接やりとりする",
      "kind": "must",
      "basis": "assumption",
      "observable": ["面接で若手の担当範囲を聞く", "採用ページの1日の流れ"]
    },
    {"id": "a2", "text": "転居を伴う異動がある", "kind": "avoid", "basis": "experience",
     "observable": ["労働条件通知書の就業場所の変更の範囲"]}
  ],
  "tradeoffs": [{"pair": ["a1", "a2"], "note": "現場に出る職種は勤務地が広がりやすい"}],
  "candidates": [
    {"label": "架空A社", "assessment": [
      {"criterion": "a1", "status": "met"},
      {"criterion": "a2", "status": "unknown"}
    ]}
  ]
}
```

- `kind` は `must` / `want` / `avoid`。`avoid` は「あったら受けない」条件を入れる。
- `basis` は `experience` / `observed` / `assumption` / `unknown`。**想像で置いている軸を `experience` にしない。**
- `observable` は、何を見れば確認できるか。**思いつかないなら空にする。** 埋めるために、それらしい確認方法を書かない。
- `tradeoffs` は両立しにくいと自分で判断した組み合わせ。両方が `must` なら注記が出る。
- `candidates[].assessment` の `status` は `met` / `unmet` / `unknown`。**調べていないものを `unmet` にしない。**

実行:

```bash
python3 scripts/check_axis.py input.json
```

出力の `criteria` は基準ごとの確認方法の有無と根拠の強さ、`candidates` は候補ごとの未確認の割合と、満たしていない必須基準・当てはまる回避条件。**適合度の点数も順位も出ない。**

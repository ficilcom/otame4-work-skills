# 棚卸しの進め方

## 何を作るか

棚卸しの成果物は、応募書類でも自己PRでもない。**後から書類にも面接にも使える、事実の一覧**である。ここで文章を整えない。整えるのは `entry-sheet-review` の仕事であり、話す順序を決めるのは `interview-prep` の仕事になる。

先に文章にすると、事実の確認が飛ばされる。順序を逆にしない。

## 洗い出す順序

1. **在籍期間を先に並べる。** 会社、部署、期間。ここが埋まらないうちに個別の経験に入らない。職務経歴書は時系列で読まれるため、期間の抜けは最初に見つかる。
2. **期間ごとに、担当した仕事を並べる。** 成果が出たものだけを選ばない。日常の業務、うまくいかなかったこと、引き継いだこと、やめたことも並べる。選別は後で行う。
3. **各経験を事実に分解する。** 下の4項目に分ける。ここで書けない項目があることが、棚卸しの結果である。無理に埋めない。
4. **裏づけを確認する。** 何に基づいて言えるのかを、経験ごとに記録する。
5. **数値を確認する。** 覚えている数値と、資料で確認できる数値を区別する。

## 事実の分解

| 項目 | 何を書くか | 埋まらないとき |
| --- | --- | --- |
| 状況 | 何が起きていたか。誰の、どんな問題だったか | 当時の資料や関係者に確認する |
| 行動 | **自分が**やったこと。決めたこと、手を動かしたこと | チームの行動しか書けないなら、そう記録する |
| 結果 | 何がどう変わったか。変わらなかったなら、そう書く | 結果が不明なら不明と記録する |
| 役割 | 自分が決めた（owner）、担当範囲が明確（member）、チームの一員として（team） | 曖昧なまま `unstated` にしておく |

**「チームで達成した」を「自分が達成した」に書き換えない。** 面接で必ず崩れる。役割が team なら team のまま記録し、その中で自分が何をしたかを別に書く。

## 裏づけの階層

`company-research` の出典階層と同じ考え方を、自分の経験に当てはめる。

| evidence | 何に基づくか | 強さ |
| --- | --- | --- |
| `public` | 公開されている（プレスリリース、公開資料、公開リポジトリ、受賞） | 強い |
| `record` | 手元の資料で確認できる（自分の記録、評価面談の資料、成果物） | 強い |
| `third_party` | 当時を知る人が覚えている（元同僚、上長） | 中 |
| `memory` | 自分の記憶だけ | 弱い |
| `unknown` | まだ確認していない | 未確認 |

**弱い裏づけの経験を書いてはいけない、という意味ではない。** 書けるが、書き方が変わる。資料で確認できない数値を断定形で書かない、程度の話である。`memory` と `unknown` を混ぜない。未確認は未確認として残す。

## 数値の扱い

- 覚えている数値と、確認した数値を分けて記録する。応募書類に書けるのは、確認できたものか、確認できないと分かったうえで表現を調整したものだけである。
- 数値が出ない仕事もある。**数値を作らない。** 「約」「およそ」で断定を避けたつもりの推測値を書かない。
- 数値が出ない場合は、規模（人数、期間、対象範囲）や、前後の変化を言葉で確認する。

## 経験の種類

偏りを見るために分類する。優劣ではない。

| kind | 例 |
| --- | --- |
| `build` | 新しく作った、立ち上げた |
| `improvement` | 既にあるものを改善した |
| `operation` | 継続して回した、守った |
| `people` | 育成、採用、チーム運営 |
| `sales` | 売った、交渉した、折衝した |
| `research` | 調べた、検証した、企画した |
| `other` | 上のどれにも入らない |

すべてが同じ種類に寄っている場合、他の種類の仕事を思い出せていない可能性がある。**足りない種類を作り出すのではなく、漏れていないかを確認する。**

## 守秘の線引き

棚卸しの段階で、外に出せない情報に印を付けておく。未公開の数値、顧客名、契約条件、社内資料の内容、未公開の技術情報。

印を付けた経験は、書類と面接で**どう抽象化するか**を先に決める。「大手小売のクライアント」「月間数千万円規模の決済」のように、規模感を保ったまま特定できない形にできるかを確認する。できないなら、その経験は使わない判断もある。

## 新卒の場合

在籍期間の代わりに、学業、部活・サークル、アルバイト、インターン、個人の活動を並べる。同じ4項目に分解する点は変わらない。

- 成果の大きさより、**行動の具体性と、そこから何を得たか**が読まれる。数値がないことを問題として扱わない。
- 「ガクチカ」を1つに絞る前に、まず複数並べる。絞るのは応募先が決まってからでよい。

## スクリプト入力

`scripts/check_inventory_coverage.py` は、棚卸しの網羅と裏づけを数えるだけで、経験の価値も本人の適性も判定しない。

```json
{
  "track": "chuto",
  "as_of": "2026-08",
  "timeline": [
    {"label": "架空A社", "start": "2019-04", "end": "2022-03"},
    {"label": "架空B社", "start": "2022-04", "end": null}
  ],
  "experiences": [
    {
      "id": "e1",
      "title": "在庫管理システムの刷新",
      "timeline_label": "架空A社",
      "period": {"start": "2020-06", "end": "2021-03"},
      "kind": "improvement",
      "role": "owner",
      "situation": "欠品が慢性化していた",
      "actions": ["要件を定義した", "在庫の引当ロジックを実装した"],
      "outcome": "欠品が減った",
      "metrics": [{"text": "欠品率12%から4%", "evidence": "record"}],
      "evidence": "record",
      "confidential_risk": false
    }
  ]
}
```

- `as_of` は、在籍中（`end` が `null`）の期間がある場合に必要。棚卸しをしている時点の年月を入れる。
- `timeline_label` は、その経験がどの在籍期間のものか。決まらないうちは省略する。**推測で割り当てない。**
- `role` は書類の書き方ではなく、**実際の担当範囲**を入れる。曖昧なら `unstated` のままにする。
- `evidence` は経験全体の裏づけ、`metrics[].evidence` は数値ごとの裏づけ。数値だけ裏づけが弱いことがあるため、別に持つ。
- `situation` / `outcome` は、埋まっていない項目を見るために有無だけを使う。文章の質は判定しない。**埋めるために推測を書かない。**

実行:

```bash
python3 scripts/check_inventory_coverage.py input.json
```

出力の `coverage` は在籍期間ごとの棚卸し済みの月数と、連続して空いている最長の月数。`experiences` は経験ごとの不足項目と裏づけの強さ。`flags` は書類に進む前に埋めるべき点。網羅率は**棚卸しの進み具合**であって、経歴の充実度ではない。

# 報告書形式

## 1. 体験の概要

業務名、期間、実施済みの実働、事前に合意した基準の数、後から足した期待の数を1行で書く。無償の見学・学習なら、成果ではなく学習の振り返りであることを先に書く。

## 2. 事前の基準と結果

| 基準 | 事前合意 | 結果 | 観察事実（誰が何で確認したか） | 企業の支援の影響 |
| --- | --- | --- | --- | --- |

- `met` / `partial` / `not_met` / `unverified` を区別して書く。**未確認を未達と書かない。**
- 後から足した期待は表の下に分け、「次回の計画の改善点」として書く。評価の根拠にしない。
- 支援の遅れや未提供が関わる基準は、その事実を先に書く。

## 3. 基準外の観察事実

事前の基準に結びつかない職務上の事実（質問の仕方、レビューへの反映、連絡の取り方など）を、観察者付きで並べる。印象や伝聞は入れない。職務と無関係な事柄は書かない。

## 4. 企業の支援と制約

説明、資料、権限、レビューの提供状況と、遅れがあった場合の影響。次回の受け入れで直す点をここに書く。

## 5. 精算

| 項目 | 内容 |
| --- | --- |
| 報酬の基準 | |
| 実施済みの実働 | |
| 精算額 | 実施済みの実働に対する額。評価と分ける |
| 減額の有無 | 書面の検収基準に沿う場合だけ。基準の項目を示す |
| 支払時期・主体 | 契約条件のとおり |

無償のやり直し、賃金ゼロ、無期限の延長を提案しない。

## 6. 受け入れ担当者用のメモ

候補者に送らない内容。確認できたこと、確認できなかったこととその確かめ方、次の対応の候補（継続、採用の提案、追加確認、見送り）と、誰がいつまでに決めるか。他候補者との比較はここにも書かない。

## 7. 候補者に送るフィードバック案

[フィードバック案の組み立て](debrief-method.md#フィードバック案の組み立て) に沿って書く。

- 事前の基準ごとの作業事実、よかった点、改善・追加で確かめたい点
- 企業側の支援の状況と、遅れがあればその影響と詫び
- 精算の扱い
- 決まっている次の対応。決まっていなければ、いつまでに返すか

企業が決めていない継続や採用を通知にしない。内部メモと他候補者の情報を混ぜない。

## 8. 送る前に確認すること

宛先、送る時期、精算の条件が契約条件と一致しているか、次の対応が本当に決まっているか。送信・精算・採用の判断は利用者が行う。

## 引き継ぎ

- 精算の条件は `trial-contract-terms` で決めたものに従う。食い違いがあればそちらに戻す。
- 継続や採用の提案に進むなら、条件の設計は `trial-work-design`（継続の業務）か、雇用に切り替える場合は労働条件の明示として別に扱う。
- 次回の受け入れで直す点（支援の遅れ、基準の言語化不足）は、`trial-work-design` と `trial-listing-draft` に戻す。

## 書かないこと

- 候補者の性格、適性、将来の活躍の断定
- 職務と無関係な属性に基づく評価
- 後から足した期待を根拠にした評価
- 未確認を未達にした記述
- 成果への満足や採用判断を反映した精算、無償のやり直し、賃金ゼロ
- 他候補者の情報、内部の評価メモ
- 決めていない継続や採用の通知

# 応募者への返信の作り方

## 前提

応募者への返信は、募集文に書いた条件の続きである。募集文にない業務や日程を返信で出せば、それは新しい提案であって、本人が同意した条件ではない。返信の前に、募集文と受け入れ計画の条件を手元に置く。

返信の目的は4つに分かれる。目的が決まるまで文面を書かない。

| 目的 | いつ | 返信に入れるもの |
| --- | --- | --- |
| 招待（`invite`） | 必須要件が応募内容で確認でき、受け入れの準備がある | 次の段階（面談か開始前の確認）、日程の候補、開始前に確かめる質問 |
| 質問（`ask`） | 必須要件が一部しか確認できない、稼働や条件に確認がある | 確認質問と、なぜ聞くか。回答の期限は目安として書く |
| 保留（`hold`） | 社内の判断や予算が決まっていない | いつまでに返すか。理由を詳しく書かなくてよいが、待たせる期間は書く |
| 辞退（`decline`） | 確認済みの事実で、今回の募集に合わない | 募集の要件に照らした事実。理由を書くかは利用者が決める |

## 照合の仕方

1. 募集文の要件を、必須と歓迎に分けて書き出す。募集文に書いていない要件を後から足さない。足すなら、それは募集文の修正であって応募者の評価ではない。
2. 要件ごとに、応募内容（応募文、プロフィール、ポートフォリオ、チャット、面談）から確認できる範囲を記録する。示している（`shown`）、一部示している（`partial`）、書かれていない（`not_shown`）、未確認（`unknown`）を分ける。
3. **応募者が述べていないことを推測で埋めない。** 「この職歴ならCMSも使えるだろう」は根拠ではない。推測は未確認に戻し、確認質問にする。
4. 書かれていない必須要件は、書いていないだけか、経験がないかを確かめる。応募文は短いことが多く、書かれていないことと持っていないことは同じではない。
5. **職務と無関係な属性（年齢、性別、婚姻、国籍、居住地の近さなど）を照合に使わない。** 募集文にそうした要件が入っていたら、照合から外し、募集文の修正点として `trial-listing-draft` に返す。

## 返信で詰まりやすいところ

- **確認前に辞退にしない。** 必須要件が未確認のまま辞退の返信を書くと、応募者は理由が分からず、企業は候補を見落とす。先に質問を送るか、確認済みの事実だけで判断する。
- **他の応募者を返信に書かない。** 「他に経験豊富な方がいたので」は、他候補者の情報であり、本人への説明にならない。募集の要件と本人の応募内容だけで書く。
- **内部の評価メモを返信に混ぜない。** 受け入れ担当者用のメモと候補者に送る文面を分けて作る。
- **募集文にない業務・日程は提案として書く。** 「追加で1本お願いします」を既定の条件にしない。実働・報酬・期間が変わるなら、`trial-work-design` で計画を作り直してから提案する。
- **稼働の不足を辞退の理由にしない。** 応募者の週の稼働が計画より少ないなら、範囲を減らす案か期間を延ばす案を返信に添える。どちらを選ぶかは双方が決める。
- **返信の期限を守れないなら保留の返信を先に送る。** 待たせる期間を書く。理由の詳細は要らない。
- **同じ募集に複数の応募者がいる場合、返信は1人ずつ作る。** 仮名で管理し、文面の使い回しで他候補者の名前や条件が残らないようにする。

## 返信文の構成

1. 応募への礼と、何についての返信か（募集名）
2. 応募内容のどこを読んだか（本人が書いた事実に触れる。評価の言葉は要らない）
3. 目的に応じた本文：次の段階と日程の候補／確認質問／待たせる期間／辞退の事実
4. 条件の確認：募集文の条件を変えないこと、変える場合は提案であること
5. 返信の期限の目安と、連絡の手段

文面は利用者の発言と応募内容にある事実だけで作る。企業の魅力、採用後の条件、応募者の能力の評価を創作しない。

## スクリプト入力

`scripts/check_applicant_fit.py` は、要件と応募内容の照合を数え、返信案に混ぜてはいけないものを見つけるだけで、応募者の適性も採用の成否も判定しない。

```json
{
  "as_of": "2026-09-17",
  "requirements": [
    {"code": "editing", "label": "記事編集の経験", "required": true},
    {"code": "cms", "label": "CMSの操作", "required": false},
    {"code": "weekday", "label": "平日日中に1時間の合同レビュー", "required": true}
  ],
  "evidence": [
    {"requirement": "editing", "status": "shown", "source": "application", "note": "架空の媒体で2年"},
    {"requirement": "cms", "status": "unknown"},
    {"requirement": "weekday", "status": "partial", "source": "chat", "note": "水曜のみ可"}
  ],
  "reply": {"purpose": "ask", "includes": ["questions", "next_step"]},
  "reasoning": {"non_job_attributes": [], "compares_other_candidates": false},
  "proposals": [
    {"topic": "合同レビューを水曜に固定", "agreed": false, "presented_as": "proposal"}
  ],
  "availability": {"candidate_weekly_hours": 4, "required_weekly_hours": 6}
}
```

- `requirements` は募集文の要件。`required` の省略は必須として扱う。`job_related` を `false` にすると、照合と質問から外れ、募集文の修正点として注意が出る。
- `evidence` は要件ごとの応募内容の確認結果。`status` は `shown` / `partial` / `not_shown` / `unknown`。`source` は `application` / `profile` / `portfolio` / `chat` / `interview` / `assumed` / `unknown`。**`assumed`（推測）は根拠にならず、`unknown` に戻される。** `not_shown` は、出所が `interview` か `chat`（本人に直接聞いた）のときだけ「持っていない」の確認になる。応募文やプロフィールに書かれていないだけなら省略として扱い、辞退の根拠にしない。
- `reply.purpose` は `invite` / `ask` / `hold` / `decline` / `unknown`。`reply.includes` は返信案に入れようとしているもので、`questions` / `next_step` / `conditions` / `other_candidates` / `internal_notes` / `new_work` / `new_dates` / `reason_for_decline` から選ぶ。
- `reasoning` は、利用者が返信の判断に使おうとしている理由のうち募集文にないもの。`non_job_attributes` に年齢や家族構成など職務と無関係な属性が入っていれば、判断に使わないよう注意が出る。`compares_other_candidates` が `true` なら、比較を返信に持ち込まないよう注意が出る。募集文にそうした要件が書かれている場合は、`requirements` 側で `job_related: false` にする。
- `proposals` は返信で出す提案。`agreed` が `true` でないのに `presented_as` が `agreed` なら注意が出る。
- `availability` は応募者の週の稼働と、計画の週の実働。少なければ、辞退ではなく調整案を添えるよう注意が出る。計画の週の実働が分からなければ、利用者に確かめる。どちらかが欠けたままなら比較しない。
- 歓迎要件が応募内容に書かれていない場合（`not_shown`）も質問の候補に出るが、`required: false` が付く。聞くかどうかは利用者が決め、応募の判断には使わない。

実行は標準入力から渡すのを既定にする。応募内容をファイルに残さないためである。ファイルに書いた場合は `python3 scripts/check_applicant_fit.py input.json` で読み、終わったら消す。

```bash
python3 scripts/check_applicant_fit.py <<'JSON'
{"requirements": [{"code": "editing", "label": "記事編集の経験"}], "evidence": [], "reply": {"purpose": "ask"}}
JSON
```

出力の `summary` は必須要件の確認状況の数、`coverage` は要件ごとの確認結果、`questions` は確認質問にする要件、`readiness` は返信案としてどこまで進められるか、`flags` は送る前に直す点である。`readiness.status` が `ready_for_owner_review` でも、送信は利用者が行う。

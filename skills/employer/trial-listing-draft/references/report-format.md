# 報告書形式

## 1. 募集の骨格

先頭に、募集の種類（有償業務／無償の見学・学習）、対象（経験者／未経験者／問わない）、原稿の段階（内部検討用／掲載用の下書き／掲載済みの点検）を1行で書く。

**有償業務か無償の見学・学習かが決まっていない場合は、その一点を最初に書く。** 必須項目が変わるため、他の点検より優先する。

## 2. 項目の記載状況

| 項目 | 必須 | 記載 | 本文の要点 | 直し方 |
| --- | --- | --- | --- | --- |

- `stated` / `missing` / `unclear` / `unknown` を区別して書く。**未確認を「記載なし」と書かない。**
- 本文の要点は原稿の文言をそのまま写す。「一式」「随時」「納得いくまで」は言い換えずに残す。
- 必須項目を先に並べ、任意の項目を後に置く。

## 3. 表現の点検

掲載前に直す表現（範囲が閉じていない、無償の実務、採用の保証、職務と無関係な属性）と、確認して残すか決める表現（上限の表現、根拠を示せない訴求）を分けて並べる。各項目に、該当箇所、なぜ候補者の判断を妨げるか、置き換え案を添える。

## 4. 数字の整合

| 数字 | 値 | 出所 |
| --- | --- | --- |
| 実働の合計 | | 計画 |
| 週の稼働 × 期間 | | 計画 |
| 報酬の基準と予定費用 | | 計画 |
| 予算 | | 社内 |

収まらない組み合わせがあれば、どれを変えるかの選択肢を並べる。**期間だけ延ばしても総額は変わらない。** 選ぶのは利用者である。

## 5. 募集文の下書き

内部検討用と掲載用を分けて出す。

**内部検討用**には、予算、担当者の工数、未確定の条件と確認先、候補者に見せない前提を含める。

**掲載用の下書き**は、[項目一覧](listing-items.md) の順に沿って、次の構成で書く。

1. 任せる作業と対象（何を、いくつ）、成果物と完了基準、対象外の作業
2. 必要な経験と使う道具。未経験者向けなら、無償の見学・学習の活動内容
3. 企業の支援：説明担当、資料、レビューの機会、質問の受け方
4. 時間：実働の合計、期間、週の稼働、実施する時間帯、場所とリモートの可否
5. 報酬：有無、基準、契約形態、支払時期、経費の扱い
6. 応募後の流れ、開始までの目安、体験後の扱い（採用や継続を保証しないこと）
7. 秘密情報の扱いがあればその範囲

未確定の値は本文の中で ［時給○円］ のように角括弧の空欄にし、値を埋めない。何を決めれば埋まるかは下書きの外に確認事項として残す。**企業の魅力、採用後の条件、候補者の実績を創作しない。** 利用者の発言と計画にないことは書かない。

## 6. 掲載前に解消すること

上の2〜5から、順に並べる。各項目に、誰が確認するか（社内の決裁者、受け入れ担当者、サービス運営）、何が確認できれば解消するか、本文のどこが変わるかを添える。

掲載の操作と最終判断は利用者が行う。点検の結果が `ready_for_owner_review` でも、掲載を勧める結論を書かない。

## 引き継ぎ

- 実働・期間・報酬の数字が決まっていない場合は、`trial-work-design` で計画を作ってから本文に戻る。
- 予算が社内で通っていない場合は、`trial-budget-brief` で社内説明を作る。
- 契約形態・支払時期・秘密情報の扱いを本文に書く前に、`trial-contract-terms` で発注側の明示事項を確認する。
- 応募が来たら `applicant-reply` に渡す。募集文に書いた条件が、返信で変わらないようにする。

## 書かないこと

- 応募が集まるか、何人来るかの見込み
- 掲載してよい、という結論
- 相場で補った単価、記憶で補ったサービス条件
- 企業の魅力、採用後の条件、候補者の実績の創作
- 職務と無関係な属性による絞り込み
- 採用や継続の保証

# 募集文に書く項目と表現

## 前提

おためし転職の募集文は、候補者が**応募するかどうかを判断するための情報**である。企業の魅力を伝える前に、何を、どのくらいの時間で、どんな支援のもとで、いくらで行うのかが書かれていなければ、応募は集まらないか、応募後の条件調整で崩れる。求職者側は `job-posting-analysis` で募集文を「書いてあること」と「書いていないこと」に分けて読む。ここでは同じ基準を書き手の側から使う。

募集文は有償業務と無償の見学・学習で必須項目が違う。**企業の実務を担うなら経験にかかわらず有償業務として書く。** 「体験」「研修」の名称で実務を無償にしない。

## 項目一覧

| code | 項目 | group | 有償業務 | 見学・学習 |
| --- | --- | --- | --- | --- |
| `work_content` | 任せる作業の内容と対象（何を、いくつ） | `work` | 必須 | 必須（活動の内容） |
| `deliverable` | 成果物または実施内容と完了基準 | `work` | 必須 | 任意 |
| `out_of_scope` | 対象外の作業 | `work` | 必須 | 任意 |
| `experience_required` | 必要な経験と使う道具 | `work` | 必須 | 任意 |
| `support` | 企業の支援（説明担当、資料、レビュー） | `support` | 必須 | 必須 |
| `contact_role` | 受け入れ担当者の役割 | `support` | 任意 | 任意 |
| `hours` | 実働の見込み（合計時間） | `time` | 必須 | 必須 |
| `schedule` | 期間、週の稼働、実施する時間帯 | `time` | 必須 | 必須 |
| `location` | 実施場所とリモートの可否 | `time` | 必須 | 必須 |
| `compensation` | 報酬の有無と基準（時間単価・固定額・無償） | `money` | 必須 | 必須（無償であることを書く） |
| `expenses` | 交通費・経費の扱い | `money` | 任意 | 必須 |
| `contract_form` | 契約形態 | `money` | 必須 | 任意 |
| `payment_timing` | 支払時期と支払主体 | `money` | 必須 | 任意 |
| `selection_process` | 応募後の流れと開始までの目安 | `process` | 任意 | 任意 |
| `after_trial` | 体験後の扱い（採用や継続を保証しないこと） | `process` | 任意 | 任意 |
| `confidentiality` | 秘密情報の扱い | `process` | 任意 | 任意 |

任意の項目も、書けるなら書く。応募後に必ず聞かれる項目（`selection_process`、`after_trial`）は、先に書くと確認のやり取りが減る。

## 書き手が詰まりやすいところ

- **「一式」「その他付随する業務」「柔軟に対応」は範囲ではない。** 候補者は仕事量を見積もれず、応募を見送るか、応募後に範囲の調整が始まる。`work_content` と `deliverable` と `out_of_scope` の3つが揃って範囲が閉じる。
- **「納得いくまで修正」は品質基準ではない。** 確認できる完了基準（誰が何を見て完了とするか）と、有限の修正回数・時間に置き換える。
- **報酬の「最大」「〜まで可能」は、実際に適用される条件を添えないと誤解を生む。** 求職者側のスキルは、こうした表現を欠けている条件として扱う。適用条件が書けないなら、確定している額だけを書く。
- **実働の合計、週の稼働、期間、時間単価、予算は同時に成立させる。** 「12時間・時給2,000円・予算18,000円」は成立しない。どれかを変えるまで、3つを同時に本文に書かない。
- **未経験者向けに「無償で実務を経験」と書かない。** 無償で提供できるのは見学・説明・架空データによる模擬課題までである。実務を任せるなら有償業務として書き、支援と説明の時間を本文に入れる。
- **無償体験を有償業務への応募の前提にしない。** 「まずは無償体験から」は、経験者の応募を減らす。
- **採用や継続を保証しない。** 「体験後は採用」「継続確約」と書かない。体験後の判断は双方に残ることを書く。
- **職務と無関係な属性で絞らない。** 性別、年齢、婚姻、国籍などの記載は、雇用の募集では公的な規制があり、業務委託でも職務要件に置き換える。募集の表現に関する公的資料は [公式情報の確認](source-checks.md) で確認する。
- **根拠を示せない訴求を入れない。** 「業界No.1」「急成長」は、出典を添えられないなら外す。候補者が確かめられる事実（何をしている会社か、誰が受け入れるか）を書く。
- **社内案を確定条件として書かない。** 予算や単価が社内で通っていない、支払主体をサービスで確認していない、といった条件は、本文に書く前に確定させるか、下書きに確認事項として残す。

## 内部検討用と掲載用を分ける

| 版 | 読み手 | 含めるもの | 含めないもの |
| --- | --- | --- | --- |
| 内部検討用 | 社内の決裁者、受け入れ担当者 | 予算、担当者の工数、未確定の条件と確認先、候補者に見せない前提 | なし |
| 掲載用の下書き | 候補者 | 上の項目一覧、企業の支援、応募後の流れ | 予算の内訳、内部の評価基準、未確定の条件 |

掲載用の下書きは、内部検討用の確認事項がすべて解消してから確定版にする。解消前に掲載を急ぐなら、未確定の条件を本文から外し、応募後に確認する項目として `selection_process` に書く。

## スクリプト入力

`scripts/check_listing.py` は、項目の記載状況、本文の表現、計画の数字の整合を数えるだけで、応募が集まるかも、掲載してよいかも判定しない。

```json
{
  "as_of": "2026-09-17",
  "listing": {
    "kind": "paid_work",
    "audience": "experienced",
    "stage": "internal_draft",
    "text": "既存記事3本の改善案を作成していただきます。..."
  },
  "items": [
    {"code": "work_content", "status": "stated", "note": "記事3本の改善案"},
    {"code": "deliverable", "status": "stated"},
    {"code": "out_of_scope", "status": "missing"},
    {"code": "hours", "status": "stated"},
    {"code": "compensation", "status": "unclear", "note": "「時給最大2,000円」"}
  ],
  "plan": {
    "candidate_hours": 12,
    "weekly_hours": 6,
    "period_weeks": 2,
    "compensation": {"basis": "hourly", "hourly_rate": 2000},
    "budget": 24000
  },
  "conditions": [
    {"topic": "支払主体", "agreement": "unconfirmed"}
  ]
}
```

- `listing.kind` は `paid_work`（有償業務）/ `learning_visit`（無償の見学・学習）/ `unknown`。未定なら、どちらかで必須の項目をすべて必須として見る。
- `listing.audience` は `experienced` / `inexperienced` / `any` / `unknown`。`inexperienced` で `paid_work` なら、有償枠のままにして支援を本文に書くよう注意が出る。
- `listing.stage` は `internal_draft` / `ready_to_post` / `published` / `unknown`。判定には使わず、報告で下書きを新規案にするか掲載済みの修正案にするかを分けるための情報である。
- `listing.text` は本文の原文。**前後の空白を含めてそのまま渡す。** 本文全体は出力に載らず、一致した表現だけが短く返る。
- `items` は確認した項目だけを入れる。入れなかった項目は「未確認」として数えられる。`status` は `stated` / `missing`（書かれていないことを確認した）/ `unclear`（書いてはあるが読み取れない）/ `unknown`（未確認）。**未確認を `missing` に丸めない。**
- `plan` は `trial-work-design` で決めた数字か、計画がなければ利用者の発言から仮置きした数字。入れると、実働が週の稼働×期間に収まるか、予定費用が予算に収まるかを確かめる。`compensation.basis` は `hourly` / `fixed` / `none`（無償）/ `unknown`。**単価がなければ相場で埋めない。** 仮置きの単価や予算は、確定条件として本文に書かないよう `conditions` にも `internal_draft` として入れる。
- `conditions` は本文に書こうとしている条件のうち、社内案（`internal_draft`）や未確認（`unconfirmed`）のもの。確定条件として書かないよう注意が出る。`agreement` の値は `trial-work-design` と同じ。

実行は標準入力から渡すのを既定にする。本文をファイルに残さないためである。

```bash
python3 scripts/check_listing.py <<'JSON'
{"listing": {"kind": "paid_work", "text": "..."}, "items": []}
JSON
```

ファイルに書いた場合は `python3 scripts/check_listing.py input.json` で読み、終わったら消す。

本文の表現の検査は代表的な言い回しだけを拾う。**一致しなかったからといって表現に問題がないとは限らない。** [書き手が詰まりやすいところ](#書き手が詰まりやすいところ) の一覧を正とし、スクリプトは見落としを減らす補助として使う。

出力の `checklist` は項目ごとの記載状況、`text_findings` は本文の表現（`block` は掲載前に直す、`check` は確認して残すか決める）、`numbers` は計画の数字の整合、`readiness` は点検としてどこまで進められるか、`flags` は掲載前に解消する点である。`readiness.status` が `ready_for_owner_review` でも、掲載の操作と最終判断は利用者が行う。

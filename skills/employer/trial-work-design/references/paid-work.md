# 有償おためし業務計画

企業が支払う費用と期待する仕事を検討でき、候補者も提供する時間と成果を理解できる計画を作る。評価だけのための大きな課題ではなく、実際の課題から小さく完結できる範囲を選ぶ。

## 課題を仕事量に変える

1. 解決したい課題、今回確かめたい能力・協働、予算、期限、候補者の作業経験・稼働時間を拾う。未定なら、見積もりに必要な前提を仮置きし、提案と確認事項を返す。
2. 作業を分解し、対象・件数・品質・対象外を定義する。業務が時間内の運用なら実施範囲と引き継ぎを、制作なら提出物と完了基準を決める。売上など本人が制御できない結果を保証させない。
3. 説明、準備、実作業、会議、レビュー、修正、振り返りを見積もる。候補者の実働と企業担当者の工数を別々に示す。企業単独のレビューを候補者の実働に足さず、合同レビューはそれぞれの時間として扱う。
4. 合計実働を候補者の週の稼働に収め、資料提供・返答待ちを考慮した実施期間に配置する。実働とカレンダー上の期間を分け、途中確認日を設定する。日付がなければ「開始日から2週間」のような仮案にする。
5. 提示された報酬基準と計画を突き合わせる。予算が足りなければ範囲縮小・予算増額・期間変更を比較し、何が変わるか示す。期間だけ延ばしても総実働や総額は減らない。

## 企業と候補者が確認できる計画

| 項目 | 記載する内容 |
| --- | --- |
| 目的 | 解決したい課題、体験で双方が確認したいこと |
| 業務範囲 | 対象作業、件数、対象外の業務 |
| 成果・完了基準 | 提出物または実施内容、必要な品質、確認担当者・方法 |
| 仕事量 | 作業別の実働見積もり、合計、前提と増減要因。必要なら幅を示す |
| 期間 | 開始・終了、週の稼働、途中確認、提供待ちの依存関係 |
| 企業の準備 | 資料、権限、説明担当、レビュー工数と提供予定。秘密情報・成果物の利用範囲 |
| 報酬 | 契約形態の確認、時間単価・固定額等の基準、予定総額、経費・税の含み方、支払日・主体 |
| 変更条件 | 追加業務、修正の範囲・回数・時間、超過前の相談、延長・中止時の連絡と精算 |

条件は企業の内部案、候補者への提示済み、候補者の希望、双方合意、未確認を分ける。合意には根拠を付ける。企業の内部案だけから承諾済みの募集・返信文を作らない。

## 費用と変更の扱い

- 時間単価が提示されていれば、単価×予定実働で予定額を計算する。税・経費が未定なら別記し、総費用が確定したように見せない。単価がなければ相場を創作せず、必要時間と単価確認を返す。
- 固定額は対象範囲、完了・検収、修正条件と組にする。固定額÷時間は比較用の換算であり、時間単価契約や適法性の証明ではない。企業が「納得するまで」といった無制限の修正条件は、確認可能な品質と有限の修正範囲に具体化する。
- 説明や必要な会議を無償の枠に移して予算を合わせない。工数の根拠がないまま候補者の作業速度を上げて帳尻を合わせない。
- 資料や権限が届かない場合は、影響する作業・期限と企業側の対応を示す。別作業への切り替えや提供後の再日程を提案し、候補者だけに遅れを負わせない。待ち時間の有給・無給は契約と拘束の実態を確認する。
- 追加依頼は、既存範囲との差、追加実働・費用・日程を示して合意前の案として返す。無制限の残業・修正・延長を前提にしない。
- 雇用なら成果への不満や不採用を理由に賃金をゼロにする条件は作らない。業務委託という名称だけで扱いを決めず、支払い・検収・修正条件を確認する。最低賃金や法的判断が必要なら [一次情報](source-checks.md) を確認し、専門家への質問を用意する。

## 架空の計画例

既存記事3本の改善案を作る。事実関係の根拠、構成上の問題、改善理由を各記事に添え、公開操作と新規記事の制作は対象外とする。候補者の時間は説明1時間、調査・作成6時間、合同レビュー2時間、修正2時間、振り返り1時間の計12時間。週6時間・2週間の案とし、企業は開始前に対象記事を提供し、第1週末に途中確認する。

企業が時間単価を提示している場合、その単価×12時間が予定額となる。単価や契約形態はこの例では未定。企業担当者も説明・合同レビュー・振り返りの計4時間に加え、資料準備の時間を確保できるか確認する。修正は合意した範囲で1回・計2時間を見込み、超えそうなら追加着手前に範囲・費用・日程を相談する。いずれも提案であり標準単価・標準工数ではない。

## スクリプト入力

`scripts/plan_trial_work.py` は計画を実働・期間・費用の数字に直すだけで、採用の成否も候補者の適性も判定しない。

```json
{
  "as_of": "2026-09-17",
  "plan": {
    "label": "架空の記事改善おためし業務",
    "candidate_weekly_hours": 6,
    "period": {"start": "2026-10-01", "end": "2026-10-14", "checkpoint": "第1週末に途中確認"}
  },
  "tasks": [
    {"label": "説明", "kind": "learning", "paid": true, "candidate_hours": 1, "company_hours": 1},
    {"label": "改善案の作成", "kind": "company_work", "paid": true, "candidate_hours": 6, "candidate_hours_max": 8},
    {"label": "合同レビュー", "kind": "company_work", "paid": true, "candidate_hours": 2, "company_hours": 2},
    {"label": "修正（合意した範囲で1回）", "kind": "company_work", "paid": true, "candidate_hours": 2},
    {"label": "振り返り", "kind": "learning", "paid": true, "candidate_hours": 1, "company_hours": 1},
    {"label": "資料準備", "kind": "company_work", "paid": true, "company_hours": 2}
  ],
  "compensation": {
    "basis": "hourly",
    "hourly_rate": 2000,
    "expenses_included": false,
    "payment_date": "2026-11-30"
  },
  "budget": {"amount": 30000, "includes_expenses": false},
  "revisions": {"rounds": 1, "hours": 2},
  "conditions": [{"topic": "報酬", "value": "時間単価2000円", "agreement": "internal_draft"}]
}
```

- `kind` は `learning`（見学・学習）/ `mock`（模擬課題）/ `company_work`（企業の実務）/ `unknown`。**企業の実務を `learning` にしない。** `company_work` が `"paid": false` だと注意が出る。資料準備のような企業単独の作業も、その実務に属するなら `company_work` でよい。
- **修正と振り返りも作業として入れる。** `revisions` は修正の範囲が閉じているかを見るだけで、時間を合計に足さない。修正の実働は `tasks` に入れないと予定費用から抜ける。
- `paid` は有償枠かどうか。決めていないなら省略する。省略は「未定」であって無償ではない。**予定費用は `"paid": true` の作業だけで計算する。** 無償と未定の時間は別に出るので、説明や会議を無償枠へ移して予算を合わせると数字に表れる。
- `candidate_hours` は候補者の実働、`company_hours` は企業担当者の工数。**合同作業は双方に入れる。** 資料準備のような企業単独の作業は `company_hours` だけに入れる。この2つは合計されない。
- 見積もりに幅があるときだけ `candidate_hours_max` を足す。予算との突き合わせは上限側で行う。
- `basis` は `hourly` / `fixed` / `none`（無償の見学・学習）/ `unknown`。単価が未定なら `hourly_rate` を省略する。**相場を創作しない。** `none` の計画に `company_work` があれば注意が出る。`none` なら予算の突き合わせと修正範囲の注意は出ない。
- `expenses_included` と `tax_treatment` は決まった扱いだけを書く。「確認する」のような未確認の文言を入れると決まった扱いに見えるので、未確認なら省略する。
- `budget.amount` は今回の予算。省略すると「未入力」として注意が出る。
- `revisions` は修正の回数と時間の範囲。「納得するまで」のように上限がないものは省略し、具体化すべき項目として扱う。**修正なしで合意しているなら `{"rounds": 0, "hours": 0}` と書く。** 省略（未定）と0（合意済み）は別物である。見学・学習だけの計画では省略してよい。
- `plan.period` の日付が未定なら、仮の開始日を置き、仮であることを報告に書く。1週間に満たない期間（1日の見学会など）は、その週に全実働が入るものとして週あたりの値を出す。
- `agreement` は `internal_draft`（企業の内部案）/ `offered`（候補者に提示済み）/ `candidate_request` / `mutual` / `unconfirmed`。**`internal_draft` と `unconfirmed` を、提示済みや合意済みとして募集文・返信文に書かない。**

実行:

```bash
python3 scripts/plan_trial_work.py input.json
```

出力の `workload` は実働の内訳（有償・無償・未定を分けた時間と、企業担当者の工数）、`schedule` は期間に配置したときの週あたりの実働、`cost` は予定費用と時間換算、`budget` は予算との差、`flags` は候補者に提示する前に確認すべき点。期間だけを延ばしても `cost` は変わらない。

時間換算は2通り出る。`effective_hourly_paid_*` は予定費用を**有償時間**で割ったもの、`effective_hourly_all_*` は**無償の作業も含めた候補者の全実働**で割ったものである。説明や会議を無償枠へ移すほど後者は下がるので、帳尻合わせが数字に表れる。

見積もりの欠けた作業があるうちは、予算に収まるか（`budget.over`）と週あたりの実働が収まるか（`fits_candidate_availability`）を判定せず `null` にする。`budget.decidable` が `false` のとき、予算内と読まない。

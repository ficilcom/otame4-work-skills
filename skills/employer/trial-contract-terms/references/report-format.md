# 報告書形式

## 1. いま条件がどこまで書けているか

先頭に1行で状態を書く。条件を何に書いているか（契約書、発注書、メール、サービス画面、チャット、口頭、未着手）、着手予定日、着手前に確定させる項目のうち書面で示せている数と開いている数。

**まだ何にも書いていない場合は、その一点を最初に書く。** 以降の項目がすべて未確定であることを示すため、他の分析より優先する。

雇用として受け入れる計画なら、ここで先に書く。労働条件の明示が論点になるため、この確認表は使わない。

## 2. 明示事項の確認表

| 項目 | group | 記載 | 出所 | 書面か | 文言の要点 | 直し方 |
| --- | --- | --- | --- | --- | --- | --- |

- `stated` / `missing` / `unclear` / `unknown` を区別して書く。**未確認を「記載なし」と書かない。**
- 文言の要点は、書いた文言をそのまま写す。「納得するまで」「随時」「柔軟に」は言い換えずに残す。
- 対象外の項目（成果物を納めてもらわない業務の修正回数など）は、対象外と明記する。
- **着手前に確定させる項目**を先に並べ、残りを後に置く。

## 3. 報酬と支払い

| 見方 | 内容 | 前提 |
| --- | --- | --- |
| 予定額 | | 報酬の決め方と、含まれている実働 |
| 支払いの条件 | | 成果や採用判断に左右されないか |
| 中止時の精算 | | 実施済みの実働を支払うか |
| 源泉徴収・消費税・経費 | | 扱いを書いたか（税額は計算しない） |

## 4. 支払までの日数

- 受領日と支払期日を並べ、日数を書く。検査がある場合は検査完了日からの日数も参考として添える。
- 起点を受領日にするか検査完了日にするかの定めは公表資料で確認し、書面に書いたかを示す。参照する上限との比較は受領日起点で行う。
- 参照する上限の日数は、利用者が一次情報で確認した値を使う。確認していない場合は、日数だけを出し、比較しないと書く。
- 支払期日を書いていない場合は、それ自体を着手前の項目の先頭に置く。

## 5. 修正と解除

修正の回数・時間の上限と、超えたときの扱い（追加の発注）。中途解除を双方がどう行えるか、予告、実施済みの実働の精算。企業側だけの解除、無償の修正、上限のない修正があれば、置き換え案を添える。

## 6. 候補者に提示する前に直すこと

上の2〜5から、順に並べる。各項目に、何を書き足すか、誰が決めるか（社内、サービス運営への確認、専門家への確認）、着手前に必要か、進めながらでよいかを添える。

**着手前に書面で確定させるもの**と、**進めながら決めてよいもの**を分ける。

## 7. 条件を書いた文面の下書き

候補者に送る条件の文面を、[項目一覧](required-terms.md#項目一覧) の順で下書きする。未確定の項目は空欄にし、「確認中」と書く。相場や慣行で埋めない。サービスの契約画面を使う場合は、その画面に載らない項目を別途メールで示す形にする。

## 引き継ぎ

- 範囲・実働・報酬の数字は `trial-work-design` の計画から写す。数字が変わったら計画に戻す。
- 募集文に書いた条件と食い違いがあれば、`trial-listing-draft` に戻して募集文を直すか、候補者に差分を示す。
- 候補者への提示の文面は `applicant-reply` の招待の返信に添える。
- 体験が終わったら、ここで決めた検収と精算の条件を `trial-feedback` に渡す。

## 書かないこと

- 条件が適法か違法かの断定
- 相場や慣行で補った単価、支払条件
- 源泉徴収、消費税を織り込んだ手取りの計算
- 成果への満足や採用判断を支払いの条件にする定め
- 候補者に不利な条件を通す交渉の見込み

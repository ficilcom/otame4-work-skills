# 深掘りされる箇所

## 面接は書類の答え合わせから始まる

面接官は、提出済みの書類を読んだうえで質問する。**準備の起点は「何を話したいか」ではなく「書類のどこを聞かれるか」**である。書類を見ずに想定質問を作らない。

書類を出した後に気づいた誤りや誇張は、面接で必ず表に出る。書類の表現を事実に合わせる作業は、想定質問より先に行う。ここで直せない場合は、面接で聞かれたときにどう答えるかを先に決めておく。

## 掘られる箇所の型

| 型 | 何が起きているか | 準備すること |
| --- | --- | --- |
| 根拠を説明できない主張 | 書類にあるが、詳細を聞かれると答えられない | まず書類の表現を直す。直せないなら、事実の範囲で言い直せるようにする |
| 主語がチームのまま | 「チームで」「携わった」で担当範囲が読めない | 自分が決めたこと、手を動かしたこと、他者がやったことを分ける |
| 数値のない成果 | 成果を主張しているが、測った指標がない | 指標、変化の幅、期間を確認する。出せないなら何をもって成果としたかを言う |
| 再現の条件が不明 | 成果は書いてあるが、何が揃っていたから出せたのかが不明 | 体制、権限、期間を整理し、応募先で同じ条件が揃うかを見る |
| 職歴の空白 | 在籍のない期間がある | 何をしていたかを事実で説明する。無理に価値づけしない |
| 在籍期間の重なり | 副業、兼業、出向、または記載の誤り | どれなのかを説明できるようにする |
| 短い在籍期間 | 早期離職の理由を聞かれる | 前職の批判ではなく、次に何を求めたかで話す |
| 必須要件に対応する記述がない | 書類で答えていない要件がある | どの経験で答えるかを決める。ないなら近い経験と埋め方を用意する |
| 守秘に触れる内容 | 現職・前職の非公開情報に踏み込みかねない | 話す範囲の線引きを先に決める |

## 役割の書き分け

日本の中途採用では、担当範囲の確認に時間が使われる。次の3つを分けて言えるようにする。

1. **決めたこと** — 自分の判断で決めた範囲。決めていないなら決めていないと言う。
2. **手を動かしたこと** — 実際に自分が作った・書いた・交渉した部分。
3. **他者がやったこと** — チームや上長がやった部分。ここを曖昧にすると、後で崩れる。

「チームの成果を自分の成果として語らない」ことは、誠実さの問題であると同時に、深掘りに耐えるための実務的な要請でもある。

## 守秘の線引き

現職・前職の情報は、話してよい範囲を先に決める。

- 話さない: 未公開の売上・利益、顧客名、契約条件、社内資料の内容、未公開の技術情報
- 話せる: 自分の担当範囲、使った技術や手法の一般的な説明、公開されている情報、抽象化した規模感

「言えません」と答えることは減点ではない。**守秘を守れることは、次の職場でも同じように守るという証拠になる。** 聞かれて困る内容を、その場の勢いで話さないための線引きを、面接前に決めておく。

## 逆質問

逆質問は、企業研究で残った未確認の論点を回す場所である。`company-research` の報告書の「まだ確認できていないので面接で聞くこと」と、`job-posting-analysis` の「確認すべき質問」をそのまま持ち込む。

- 調べれば分かることを聞かない。調べたうえで確認する形にする。
- 労働条件の詳細（残業実態、評価、給与の内訳）は、聞く相手と段階を選ぶ。現場の面接官が答えられないこともある。書面での確認は `offer-terms-check` に回す。
- 「特にありません」は用意していないことの表明になる。数を揃えるより、確認したい論点を1つ確実に持つ。

## 段階による違い

| 段階 | 主に見られること | 準備の重心 |
| --- | --- | --- |
| カジュアル面談 | 相互の情報交換。選考ではないと説明されることが多い | 聞くことの準備。ただし評価されている前提で臨む |
| 一次 | 書類の裏取り、担当範囲、基礎的な適合 | 深掘りされる箇所への回答 |
| 二次 | 業務の具体、チームとの適合、再現性 | 再現の条件、応募先の状況との接続 |
| 最終 | 意思決定、条件、入社時期 | 志望の一貫性、条件の希望 |

段階が分からない場合は、一次の準備を基準にする。**どの段階でも、書類と食い違う話をしない。**

## スクリプト入力

`scripts/find_probe_points.py` は、書類の主張・職歴・必須要件から掘られる箇所を機械的に抽出するだけで、回答も評価も作らない。

```json
{
  "role": "Webアプリケーションエンジニア",
  "track": "chuto",
  "stage": "first",
  "claims": [
    {
      "id": "c1",
      "topic": "在庫管理システムの刷新",
      "source": "shokumu",
      "role_stated": "team",
      "metrics": [],
      "claims_outcome": true,
      "verifiable_by_user": true,
      "repeatable_stated": false,
      "confidential_risk": false
    }
  ],
  "timeline": [
    {"label": "架空A社", "start": "2019-04", "end": "2022-03"},
    {"label": "架空B社", "start": "2022-10", "end": null}
  ],
  "requirements": [
    {"text": "Webアプリケーションの開発経験3年以上", "kind": "must", "covered_by": ["c1"]},
    {"text": "SQLの実務経験", "kind": "must", "covered_by": []}
  ],
  "prepared": [{"topic": "self_introduction", "status": "drafted"}],
  "questions_to_ask": ["評価はどの単位で決まるか"]
}
```

- `track` は `chuto`（中途）/ `shinsotsu`（新卒）。準備する定番の論点が変わる。
- `role_stated` は `owner`（自分が決めた）/ `member`（担当範囲が明示されている）/ `team`（主語がチーム）/ `unstated`。書類の**書き方**を入れる。実際の役割ではない。
- `verifiable_by_user` は、利用者がその主張の根拠を説明できるか。**確認していないなら省略する。** `true` で埋めない。
- `metrics` は書類に書かれている数値。書かれていないものを入れない。
- `covered_by` は、その要件に答えられる主張の `id`。対応が思いつかない要件は空にする。埋めるために無関係な経験を割り当てない。
- `prepared` の `status` は `drafted`（話せる形になっている）/ `outlined`（要点だけ）/ `none`。

実行:

```bash
python3 scripts/find_probe_points.py input.json
```

出力の `probe_points` は掘られる箇所と定型の問い方、`preparation` は定番の論点の準備状況、`flags` は準備の前に潰すべき問題。`priority` は**準備の順序**であって、評価でも合否の見込みでもない。`likely_question` は問い方の型であり、実際に出る質問文でも模範解答でもない。
